## 1. Findings (ranked)

### N1 — CRITICAL: parket-accepted column types panic the whole process inside connector_arrow
`vendor/connector_arrow/connector_arrow/src/mysql/types.rs` (`create_field`): `type_db_into_arrow(db_ty).unwrap_or_else(|| todo!("db type: {db_ty}"))` — an unmapped type is a **`todo!()` panic**, not an error. The wire-name map (`types.rs::get_name_of_column_type`) produces names that `mod.rs::type_db_into_arrow` does not match:

| MariaDB column | parket accepts? (`orchestrator/schema.rs::mariadb_type_to_arrow`) | connector_arrow | Result |
|---|---|---|---|
| `MEDIUMINT` | yes → Int32 | `"mediumint"` unmapped | **panic at extract** |
| `VARBINARY` | yes → Binary | `"varbinary"` unmapped (Binary arm lists `binary` but not `varbinary`) | **panic** |
| `JSON` (MySQL-proper wire `MYSQL_TYPE_JSON`) | yes → Utf8 | `"json"` unmapped | **panic** (MariaDB aliases JSON→LONGTEXT → safe there) |
| `DATE` | yes → Utf8 | was unmapped; **fixed only by the uncommitted vendored edit** | panic on any fresh clone |
| `YEAR`, `TIME` | no — parket bails per-table (graceful, exit 1) | — | safe |

A panic unwinds through `process_table`'s `match Err(e)` (panics aren't `Err`), through the runtime, to `main`'s `.expect("join parket-main thread")` → **process abort, exit 101** — violating the 0/1/2 exit-code contract, skipping all remaining tables, and producing no per-table failure state. `filter_unsupported_columns` (`discovery.rs:20`) only excludes geometry types, so nothing upstream protects.
**Fix:** extend the vendored `type_db_into_arrow` (mediumint→Int32/UInt32, varbinary→Binary, json→Utf8, date→Utf8) **and commit it to the `oonid/connector_arrow` fork + bump the submodule pin**; independently, make parket's preflight reject any discovered type not in a known-extractable allowlist so an unmapped type is a per-table error, never a panic.

### N2 — HIGH: two-stream **insert** loop has no progress guard → infinite duplicate appends
`src/orchestrator/two_stream.rs:47–84`. R2 added the bail-guard to the update loop only. In Stream A, if `extract_max_id` yields `None` on a **full** chunk, `hwm_id` stays unchanged and the identical `build_insert_stream_query` re-runs forever, re-appending the same rows until disk fills. Trigger: `extract_id_as_i64` (`writer/hwm.rs`) only downcasts Int64/Int32/UInt64/UInt32 — a `SMALLINT`/`TINYINT` insert cursor (Arrow Int16/Int8) always returns `None`. (`full_refresh.rs` deliberately supports those widths — the two paths are inconsistent.)
**Fix:** mirror the R2 bail into Stream A (`new_max.is_none() && chunk_rows == batch_size → bail`), and add Int8/Int16/UInt8/UInt16 downcasts to `extract_id_as_i64`.

### N3 — HIGH: incremental loop still hardcodes `"id"` despite R2's claim
`src/orchestrator/incremental.rs:54,73` pass the literal `"id"` into `build_incremental_query` and `extract_hwm_from_batch`; only two-stream got the real key threaded. Consequences: (a) a PK not named `id` → SQL error, or wrong tiebreak column if an unrelated `id` exists; (b) `schema_evolution_check` can drop `id`/`ts_col` from the SELECT while the WHERE/ORDER BY still reference them — the batch then lacks the column, HWM extraction returns `None`, and R2's guard turns every full batch into a **permanent hard failure** (pre-R2 it was a silent duplicate loop; now it's a hard stop with no self-heal). Partial batches still append with `hwm=None`, preserving the old duplicate-on-rerun behavior below `batch_size`.
**Fix:** thread the discovered key column into `process_incremental`; force key+cursor columns into `select_columns` (or bail at preflight with an actionable message).

### N4 — HIGH: the vendored `date→Utf8` fix exists only as an uncommitted submodule edit
One-line diff in `vendor/connector_arrow/.../mysql/mod.rs`, uncommitted. Lost on any fresh clone / `git submodule update` → every DATE-bearing table panics (N1 class). Must be committed to the fork and the pin bumped (same delivery as N1's fix).

### N5 — HIGH (needs live verification): unsigned integers — schema created signed, batches arrive unsigned
`mariadb_type_to_arrow` matches `data_type` only (`"int"`→Int32), ignoring the ` unsigned` in `column_type`; connector_arrow emits **UInt8/16/32/64** for unsigned columns (`mod.rs` strip-suffix logic). `ensure_table` therefore creates the Delta schema signed while every batch carries unsigned Arrow types. Whether delta-rs 0.32 casts or rejects at `table.write` decides severity (reject = every unsigned table fails every run). AGENTS.md documents the UInt outputs, suggesting unsigned tables have been extracted in practice — verify with the Docker suite, then either map unsigned→wider-signed in `mariadb_type_to_arrow` or cast batches before write. Related: `extract_id_as_i64` casts `UInt64 as i64` (silent negative wrap past 2⁶³ → HWM corruption), and full-refresh keyset bails on the same overflow **after** chunk 0 already overwrote the destination (truncated table until a rerun) — `full_refresh.rs:66-70,155`.

### N6 — MED: R2 broke `cargo build --examples` (gate gap)
`examples/standalone_pipeline.rs:203,240` still call the 2-arg `extract_hwm_from_batch` → E0061 ×2 (**verified failing**). The lib-only gate (`build`, `clippy --lib`, `test --lib`) can't see it; the repo's own history (`f6d5191`) shows `--all-targets` lints are expected to be clean, and the release workflow will trip on it.
**Fix:** update the example calls; widen the standard gate to `cargo clippy --all-targets -- -D warnings`.

### N7 — MED: `hwm_has_advanced` compares timestamp strings whose formats can differ
`writer/hwm.rs:47-55`. Production is *coincidentally* safe: datetime columns arrive as Utf8 in connector_arrow's **fixed-width** `YYYY-MM-DDTHH:MM:SS.ffffff` (verified in `mysql/query.rs:203`), where lexicographic = temporal, and commitInfo round-trips + the repo's canonical seeds use the same form. The hazard: (a) a **space-separated config seed** makes equal-instant comparisons resolve by `'T' > ' '` (guard silently defeated, though no false bail); (b) any future path yielding true Timestamp arrays goes through the **trimming** formatter (`datetime.rs:84-105`, `".5"` vs `".500000"`), where equal instants compare unequal and a legitimate full batch can **spuriously bail**. The two-stream bootstrap seed (space-format `CAST AS CHAR`, `two_stream.rs:34-44`) survives on the same coincidence.
**Fix:** normalize every HWM to one canonical rendering at its entry points (config parse, commitInfo read, batch extraction, seed), or compare parsed `(micros, id)` instead of strings.

### N8 — MED: `ORDER BY <all columns>` OFFSET fallback is not a total order
`query.rs::build_full_refresh_query_paged` (C1). Case/accent-insensitive collations make distinct rows tie (`'abc'`/`'ABC'`), and TEXT/BLOB sort only by the first `max_sort_length` (default 1024) bytes — tie order can differ per page-query → rows skipped/duplicated at page boundaries on PK-less tables. Also a per-page full filesort of every column (incl. TEXT) — O(n²·log n) total + MySQL tmp-disk pressure.
**Fix:** order by a discovered UNIQUE/PRIMARY index (multi-column or non-integer is fine — `discover_indexes` already returns them) before falling back; strengthen string ordering (BINARY) when the fallback is unavoidable.

### N9 — MED (pre-existing, sharpened by C1): shutdown mid-full-refresh records `success` on a truncated table
`full_refresh.rs` breaks on shutdown after chunk 0's **overwrite**; `process_table` then writes `last_run_status="success"` (audit R4). The destination holds only the chunks written so far yet reports success. Fix together with R4 (interrupted status; or stage-and-swap).

## 4. Second-pass results (reruns completed 2026-07-06)

### 4a. Verify value-aggregates — **empirically validated** against DataFusion 53.1 (deltalake 0.32)
The auditor ran throwaway MemTable experiments, so these are measured, not reasoned.

**Confirmed bugs:**
- **VA1 HIGH (FalsePositive):** DataFusion `sum(decimal(38,10))` **silently returns wrong values on precision overflow** (measured: 2×6e27 → "1.2e27"; past i128 → negative garbage), while MySQL saturates to `9999….9999`. Any decimal column whose table sum ≥ ~1e28 → guaranteed false Discrepancy. (`verify/delta.rs:297,383` vs `verify/source.rs:232,296`)
- **VA2 MED-HIGH (FalsePositive):** decimal scale > 10 → Delta rounds per-row *then* sums; MySQL sums *then* rounds once (measured: 3×0.00000000005 → "0.0000000003" vs "0.0000000002"). Skip scale>10 columns or make source cast inside SUM.
- **VA3 HIGH (Memory/8 GB):** `latest_key_stats` (full append-log window sort) runs **before** the row-cap guard just to print a count (`verify.rs:471-490` vs cap at `:507`); the cap measures the *source* window, not the Delta log size; and `value_aggregates_latest` re-runs the full ranked CTE **once per column** in a fresh unbounded SessionContext. Fix: cap first; one multi-column aggregate query; bounded RuntimeEnv.
- **VA4 MED:** one unparseable string in a Utf8-stored numeric column (`cast('abc' as decimal)`) errors and **aborts the entire verify run** instead of yielding a per-table verdict. Use `try_cast` / per-table error capture.
- **VA5 MED (FalseNegative):** `fp_num` carries no non-null count, and the census is skipped for incremental scope → a value→NULL swap of a non-extremal `0` passes clean. Add `|n=COUNT(col)` to `fp_num`.
- **VA6 LOW:** `latest_key_stats` is HWM-unscoped while `value_aggregates_latest` is scoped (= audit V7, key path) — agrees only by construction today.

**Measured refutations (safe):** decimal & integer string rendering matches MySQL byte-for-byte (incl. −0 and padding); NULL/empty-window `∅` handling symmetric; `char_length` = code points both sides; HWM T-format self-consistent end-to-end; cap *is* applied before the per-column value CTEs.

### 4b. Orchestrator core / adapters / preflight / inspect (13 findings; top ones spot-verified)
- **O1 HIGH:** `TABLE_HWM_<t>` is validated as legal for two-stream (`orchestrator.rs:255`) but its only consumer is `incremental.rs:27` → **silently ignored** exactly where pre-seeding a huge bootstrap matters. *(verified)*
- **O2 HIGH:** Ctrl+C during full refresh: chunk 0's `overwrite` destroyed the previous complete snapshot; shutdown-break then records `success` → destructive escalation of R4. Consumers silently read a truncated table.
- **O3 HIGH:** auto-detection picks **nullable** cursors (`discovery.rs:243-253` checks name+type only) that `inspect.rs:58` itself brands `UNSAFE (nullable → NULL rows skipped)`; preflight is equally blind.
- **O4 MED-HIGH:** unknown `TABLE_MODE` values (typos, `two_stream`) silently degrade to Auto (`config/parse.rs:37-41`). *(verified)*
- **O5 MED:** two-stream cursor config silently overrides an explicit `TABLE_MODE=full_refresh` (checked first, no warning).
- **O6 MED:** `adapters.rs:157-167` `get_schema`: `Err(_) => Ok(None)` — same error-swallowing class as R1, silently disables the schema-evolution guard on a transient S3 error (×2 duplicated impls). *(verified)*
- **O7 MED:** `--check`/run parity gaps ×4: mode-override skips column validation; evolution check never run in preflight; S3 health-check object written at bucket root ignoring `s3_prefix`; local mode uses `NoopPreflightStorage`.
- **O8 MED:** unsupported-type handling inconsistent: geometry skipped gracefully, `time`/`year`/`bit` fail the whole table (and would `todo!()`-panic in the connector anyway — see N1).
- **O9–O13 (Low/Med):** failed-run state replaces (not merges) the last success's metadata; `schema_columns_hash` write-only; `types_equivalent` UInt/Timestamp arms unreachable (evolution check structurally blind to the unsigned mismatch, N5); `TABLE_TIMESTAMP` validated before mode resolution (fails tables that never use it); `--verify` mode resolution is a third divergent copy — auto-detected incremental tables verify as `Basic`; `inspect` prints "PRIMARY" without checking `key == "PRI"`; `state.json` path is cwd-relative.
- **Assessment:** mechanics are clean and well-tested; the debt is at policy boundaries — config precedence, shutdown semantics, and mode resolution living in three hand-synced copies. A shared mode-resolver + an explicit "interrupted" outcome would clear most of it.
