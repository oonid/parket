# Parket Code Audit — 2026-07-04

**Target runtime:** a single VM with **8 GB RAM**.
**Scope:** the full `src/` tree of parket (v0.1.1, commit `b59fd47`), audited against the
project's own stated objectives in `docs/project-brief.md` and `AGENTS.md`.
**Method:** one reviewer read the memory-critical paths (`extractor`, `writer`,
`orchestrator/*`, `query`, `main`) directly; five focused sub-audits covered the
two-stream writer, orchestrator control flow, discovery/query, config/state/calendar,
and the verify subsystem. Findings below are grounded in specific `file:line`
locations. This audit reads code only — no runtime reproduction was performed, so
severities on hard-to-trigger paths are marked accordingly.

## The objectives being audited against

1. **Dynamic memory management** — bound RAM by sizing batches from
   `TARGET_MEMORY_MB` and `AVG_ROW_LENGTH`. *This is the load-bearing objective for the
   8 GB VM.*
2. **Idempotent & resilient writes** — HWM advances only on a successful Delta commit; a
   crash mid-run re-runs the same batch with no loss and no duplicates.
3. **Auto-discovery** — infer schema and mode (Incremental / FullRefresh) with zero config.
4. **Zero-config type mapping** — Arrow types flow straight through, no manual mapping.

---

## Executive summary

Parket's core loop is structurally sound: batches are created fresh, moved into the
writer, and dropped each iteration; the incremental HWM is advanced only after the
Delta commit; and the two-stream MERGE path shows real, hard-won memory engineering (a
bounded `FairSpillPool`, single-partition external sort, disk spill, raised FD limits).

However, **the 8 GB budget is not actually enforced end-to-end**, and several
resilience guarantees the brief promises are only half-met. The most important issues:

- The **default** two-stream update strategy (`delete_then_append`) is documented as the
  "bounded-memory alternative" but is the opposite: it loads every incoming key into a
  `HashSet<i64>` and an `IN`-list predicate — the very thing that forced the 512 MB
  driver stack in `main.rs`. (**M1**, Critical)
- **FullRefresh pagination uses `LIMIT/OFFSET` with no `ORDER BY`** → rows silently
  skipped/duplicated across pages, plus O(n²) scan cost — on exactly the large-table
  case the memory budget exists to handle. (**C1**, High)
- **`read_hwm` swallows all Delta/S3 errors and returns `None`**, so a transient blip
  turns an incremental resume into a full re-extract with `SaveMode::Append` =
  **duplicate rows**. (**R1**, High)
- **HWM can silently fail to advance** (hardcoded `"id"` column, or a cursor column
  dropped by schema-evolution) → the batch loop re-queries the same full window forever,
  re-appending duplicates without terminating. (**R2**, High)
- **`--verify` can report a clean match on corrupted data**: there are no per-column
  SUM/MIN/MAX aggregates, the key fingerprint is XOR-only (trivial collisions), and it
  only runs when the PK is literally named `id`. (**V1–V3**, Critical/High)
- No upper bound on `TARGET_MEMORY_MB` and no `TARGET_MEMORY_MB≈RAM` sanity check, so the
  one knob that protects the VM can be set to OOM it. (**M4**)

## A. Memory & the 8 GB budget *(objective #1)*

### M1 — `delete_then_append` (the DEFAULT update strategy) is not bounded — Critical
**`src/writer/two_stream.rs:207-268`**, driven by default at **`src/orchestrator/two_stream.rs:113-120`**.

The doc-comment (lines 180-184) calls this the "bounded-memory alternative … memory stays
bounded regardless of target size." The implementation does the opposite for the *source* side:

1. `concat_batches` the whole incoming window into one `RecordBatch` (line 209),
2. `dedup_source.collect().await` — materializes the deduped copy again (line 219),
3. builds a `HashSet<i64>` over **every** incoming key (lines 223-257),
4. builds an `IN`-list predicate with **one `lit()` per key** (lines 263-264).

`main.rs:219-243` is the smoking gun: the program spawns itself on a **512 MB driver
stack + 128 MB worker stacks** precisely because "the DELETE predicate's `OR`-normalized
id list can drive plan-traversal depth into the hundreds of thousands." That is a
band-aid over this design.

**8 GB-VM impact:** with `avg_row_length=100` and `TARGET_MEMORY_MB=512`, one update batch
is ~5.3M rows. That's a `HashSet` of ~5M `i64` (~200 MB+ with hashbrown overhead) plus an
`IN`-list expression of ~5M literals, held *simultaneously* with the concatenated batch and
the collected dedup copy (~3× the payload), and a DELETE plan whose traversal depth commits
the 512 MB stack. Realistic OOM on the default path.

**Fix:** delete by key **range** (`key BETWEEN min AND max`) or by anti-join against the
source registered as a `MemTable`; never collect all keys into a Rust `HashSet` + `IN`-list.
Then the driver stack can shrink back to normal.

### M2 — Extractor materializes the entire query result in RAM — High
**`src/extractor.rs:56-58`**

```rust
let raw_batches: Vec<RecordBatch> = reader.collect::<Result<_, _>>()?;
```

Per-iteration memory *is* bounded by the SQL `LIMIT batch_size`, but within one `extract()`
call the full result is collected into a `Vec` with no streaming to the writer. Worse, this
sits on top of the `mysql` crate's default buffered `query` (the client buffers the whole
result set too), so peak ≈ (mysql client buffer) + (Arrow `Vec`) simultaneously — roughly
2× `TARGET_MEMORY_MB` before the writer even starts, and then delta-rs serializes to parquet
on top. The "hard ceiling" check (`extractor.rs:122-136`) only shrinks the *next* batch —
the oversized current batch is already resident.

**Fix:** stream batches from the reader into the writer instead of `collect()`; consider the
`mysql` streaming/`query_iter` path so the client doesn't buffer the whole set.

### M3 — `concat_batches` doubles the payload before MERGE and delete — High
**`src/writer/two_stream.rs:40`** (merge) and **`:209`** (delete)

`concat_batches(&schema, &batches)` allocates a contiguous copy while the original
`batches` Vec is still owned to end-of-scope → ~2× the source payload, and this Arrow
allocation is **outside** the bounded `FairSpillPool` so it cannot spill. On the 8 GB VM a
window sized to just fit the budget is doubled by the concat and can OOM before the MERGE's
spill machinery engages.

**Fix:** register the Vec without copying (`MemTable::try_new(schema, vec![batches])`), or at
minimum `drop(batches)` immediately after the concat to avoid the 2× overlap.

### M4 — `TARGET_MEMORY_MB` has no RAM-relative sanity bound — Med
**`src/config.rs:83-88`** (and `170-175` in `load_local`)

`0`/negative/garbage are correctly rejected, but `TARGET_MEMORY_MB=64000` loads fine and
sizes batches for ~64 GB on an 8 GB box → OOM-killed at runtime, not at config load. This is
the single knob protecting the VM; it should refuse to exceed available RAM.

**Fix:** ceiling-check or clamp with a warning (`if target_memory_mb > <ram_mb> { bail! }`),
same for `MERGE_MEMORY_MB`.

### M-note — What is done well
The cross-iteration memory discipline is genuinely good (agent-confirmed): no per-row
accumulation, no all-tables buffering; the MERGE path's bounded pool + single-partition
sort + disk spill (`two_stream.rs:43-91`) and the FD-limit lift (`main.rs:37-60`) are the
right tools. The problems above are all on the **source** side and the **default** strategy.

## B. Correctness, idempotency & resilience *(objective #2)*

### R1 — `read_hwm` turns transient S3 errors into `None` → duplicate rows — High
**`src/writer.rs:221-228`** (and `read_insert_hwm`, **`src/writer/two_stream.rs:163-167`**)

```rust
let table = match self.open_table(table_name).await {
    Ok(t) => t,
    Err(_) => { /* "table does not exist" */ return Ok(None); }
};
```

The `Err(_)` arm cannot distinguish "table doesn't exist yet" from "S3 timed out / 5xx /
throttled." On a transient failure it returns `None`; `process_incremental`
(`incremental.rs:25-36`) then falls back to the config seed or a from-scratch scan and
re-extracts with `SaveMode::Append` → **duplicate rows** in the Delta table. The test
`read_hwm_s3_error_returns_none` even locks this in as intended.

**Fix:** only map the genuine not-a-table errors to `None` (as `ensure_table` already does at
`writer.rs:125-129`); propagate every other error so the run fails and retries the same batch.

### R2 — HWM can silently fail to advance → infinite duplicate-append loop — High
**`src/orchestrator/incremental.rs:70-81,107`** + **`src/writer/hwm.rs:9-11`**

`extract_hwm_from_batch` hardcodes `batch.column_by_name("id")?` (`hwm.rs:11`) and returns
`None` if either the timestamp column *or* an `id` column is missing from the batch. The
incremental loop advances `current_hwm` only when the HWM is `Some`, and its only exit is
`batch_rows < batch_size`. So if a full batch (`batch_rows == batch_size`) yields no HWM —
because the cursor column was dropped by the schema-evolution filter (`schema.rs:84-96`), or
a two-stream table's real key isn't named `id` — the loop re-issues the identical query
forever and re-appends the same rows each time. On the 8 GB VM this is unbounded duplicate
Delta files + log growth that never terminates.

**Fix:** thread the real key-column name into `extract_hwm_from_batch`; and if a *full*
batch produces no advanced HWM, `bail!` rather than re-querying.

### R3 — SIGTERM is not handled — Med
**`src/orchestrator.rs:324-333`** (`SignalHandler::install` awaits only `ctrl_c()`)

Containers, systemd, and cloud VMs stop processes with **SIGTERM**, not SIGINT. The
graceful "finish the current batch, then stop" path (`check_shutdown()` in every loop)
never fires under SIGTERM — the process is hard-killed mid-batch. Data survives (HWM only
advances on commit), but the designed graceful shutdown doesn't happen where it matters most.

**Fix:** add a `tokio::signal::unix::signal(SignalKind::terminate())` arm alongside `ctrl_c()`.

### R4 — Interrupted run reports success and skips remaining tables silently — Med
**`src/orchestrator.rs:167-170,209-215,294-307`**

On shutdown the per-table loop `break`s, the table is recorded `last_run_status="success"`
with partial rows, the outer loop `break`s (skipping remaining tables), and the exit-code
rule (`failed==0 && succeeded>0 → Success`) returns 0. A run of `[a,b,c,d]` interrupted after
`a` exits 0 with `b,c,d` never touched — a wrapping scheduler sees "fully complete."

**Fix:** track interrupted/skipped separately, return `PartialFailure` (1) on any incomplete
shutdown, and don't record "success" for a table cut off mid-way.

### R5 — `state.json` write is atomic-swap but not durable — Med
**`src/state.rs:52-64`**

The write does `tmp.flush()` + `fs::rename`, but never `sync_all()` on the temp file nor
fsyncs the parent dir. `flush()` only reaches the page cache; on power loss the rename
metadata can persist while the data blocks don't → empty/garbage `state.json`, which
`load_or_warn` treats as first-run → full re-extraction.

**Fix:** `tmp.sync_all()?` before rename, then fsync the parent directory after rename.

## C. Data completeness & schema *(objectives #2, #3)*

### C1 — FullRefresh OFFSET paging: skips/duplicates rows + O(n²) — High
**`src/query.rs:48-57`** used at **`src/orchestrator/full_refresh.rs:34-37`**

```rust
"SELECT {col_list} FROM {quoted_table} LIMIT {batch_size} OFFSET {offset}"
```

No `ORDER BY`. MySQL/MariaDB give no stable row order without one, so page N+1 can repeat or
omit rows page N already returned (page splits, concurrent writes, plan changes) — the Delta
table ends up with missing/duplicate records. Chunk 0 is `overwrite`, chunks 1..n `append`,
so drift is committed silently. Separately, deep OFFSET forces the DB to scan-and-discard
`offset` rows per page → O(n²) on exactly the large tables the memory budget targets.

**Fix:** keyset pagination on the PK (`WHERE pk > {last_pk} ORDER BY pk ASC LIMIT batch_size`)
— fixes both the correctness and the perf problem at once.

### D1 — New source columns silently dropped forever — Med
**`src/orchestrator/schema.rs:84-96`**

A column present in MariaDB but absent from the existing Delta schema is removed from the
SELECT with only a `warn!`; there is no additive-evolution path. After a table gains a
column, that column's data is never captured for any incremental/two-stream table — silent,
permanent partial data loss visible only as a log line on a headless VM. (This also feeds
**R2**: dropping the cursor column stalls the HWM.)

**Fix:** add the new nullable column to the Delta schema, or fail loudly instead of dropping.

### D2 — Incremental permanently drops NULL-timestamp rows — Med
**`src/query.rs:31,36`** (`WHERE {ts} IS NOT NULL …`)

Any row whose cursor column is NULL is never extracted in incremental mode and can never
advance the HWM — silent row loss with no backfill path. The `IS NOT NULL` is needed for a
correct keyset comparison, but nothing captures the NULL subset.

**Fix:** guarantee the cursor is NOT NULL at mode-detection time, or run a one-time pass for
the NULL-timestamp rows.

### D3 — Two-stream first-run seed not persisted → skipped completions — Med
**`src/orchestrator/two_stream.rs:34-44,61`**

On first run the seed `Hwm{updated_at: MAX(update_col), last_id: i64::MAX}` lives only in
memory and is committed to Delta only as a side effect of a subsequent write. If the insert
stream writes nothing and the update stream has nothing past the seed, the seed is never
stored; the next run re-seeds to a newer `MAX`, and completions landing between the two
seeds are skipped forever.

**Fix:** persist the seeded watermark immediately via an explicit HWM-only commit before the
streams run.

## D. Configuration robustness & security

### CF1 — `DEFAULT_BATCH_SIZE=0` accepted — Med
**`src/config.rs:116-122`** (and `203-209`). Every sibling numeric knob is zero-checked;
this one falls through `.unwrap_or(10000)` with no `== 0` guard. `0` yields a config that
divides by zero or never advances (zero-row batches forever) on the VM.
**Fix:** `if default_batch_size == 0 { bail!(...) }`.

### CF2 — `AVG_ROW_LENGTH` NULL becomes a hard error — Med
**`src/discovery.rs:304-306`** — the field is a non-nullable `u64`, but
`information_schema.tables.AVG_ROW_LENGTH` can be NULL (views, some engines, no stats yet).
A NULL makes sqlx return a decode error and the whole discovery step fails, instead of the
intended `None` → default-batch-size fallback.
**Fix:** decode as `Option<u64>`, map `None`/`Some(0)` → `None`.

### S1 — `#[derive(Debug)]` on `Config` leaks secrets — Med
**`src/config.rs:12`** — `Config` holds `database_url` (with password) and
`s3_secret_access_key` as plaintext; only `display_safe()` masks them. Any `{config:?}`,
`dbg!`, or `anyhow` context capturing the struct prints both verbatim. The masking design is
one careless line from being defeated.
**Fix:** hand-write `Debug` to delegate to `display_safe()`, or wrap secrets in a
`Secret<String>` newtype.

### S2 — Identifiers unescaped, HWM value interpolated — Med
**`src/query.rs:1-3,31`** — `backtick()` wraps in backticks but does not double embedded
backticks, and the HWM timestamp is inlined as `'{updated_at}'` rather than bound. Table
names come from user config; a name containing a backtick breaks out of quoting. (LIMIT/OFFSET
are `u64`, so those are safe.)
**Fix:** escape identifiers (`ident.replace('`', "``")`) and bind the HWM value as a parameter.

### S3 — `mask_secret` panics on non-char-boundary — Med
**`src/config/mask.rs:23`** — `&secret[secret.len()-4..]` slices by byte offset; a multi-byte
UTF-8 char in the last 4 bytes panics, taking down `display_safe()` logging. A masking helper
must never crash.
**Fix:** use `chars().rev().take(4)` or `char_indices`.

### pf1 — `unreachable!()` can panic and abort `--check` — Med
**`src/preflight.rs:144`** — the `(true, true) => unreachable!()` arm assumes an
auto-detected FullRefresh table can't have both an `id` column and a datetime `ts_col`, but
`has_ts` checks name+type only, not nullability — a table with a *nullable* timestamp is
FullRefresh yet hits `(true,true)` → panic, which the `Err`-collecting loop can't catch, so
the whole `--check` aborts.
**Fix:** replace with a real fallback string.

## E. Performance

### P1 — Per-batch DB reconnect and Delta log reload — Med
- `src/extractor.rs:47-51` — a fresh `mysql::Conn::new` (TCP + auth handshake) on **every**
  `extract()` call, i.e. per batch.
- `src/writer.rs:166-169,201-204` and `two_stream.rs:34-37,144-148,201-205` — each write
  rebuilds the table and calls `table.load()` (reloads the Delta log). As a table accrues
  commits over a run, log load grows, trending toward O(n²) over the batch loop.

**Fix:** reuse one pooled DB connection across a table's batches; keep an open `DeltaTable`
handle and `update()` incrementally instead of full `load()` each batch.

*(C1's OFFSET O(n²) is the other major perf item — see above.)*

## F. Verify subsystem *(supports objective #2)*

The verify feature is meant to *prove* the sync is correct. As written it can pass corrupt
data and can OOM the VM — the two failure modes it exists to prevent.

### V1 — No per-column value aggregates → value corruption passes — Critical
**`src/verify.rs:531-571`, `123-138`** — the only column-value check is a non-null COUNT
census, and field sampling explicitly excludes decimal/float/datetime/date/time. Design L3
(§3.3) requires per-column SUM/MIN/MAX. Concrete: `orders.amount` 100.00→200.00 keeps keys
and null-counts identical and `amount` is excluded from sampling → **verify reports PASS on
corrupted money.**
**Fix:** add type-appropriate SUM/MIN/MAX (datetime parsed semantically) on both probes.

### V2 — Key fingerprint is XOR-only → collision false-pass — High
**`src/verify.rs:149-157,256-263`** — `SUM(id)` was dropped; the fingerprint is
count/distinct/min/max/xor. XOR has a trivial collision family: source `{1,3,5,8}` vs delta
`{1,2,4,8}` share distinct=4, min=1, max=8, xor=15 → **PASS despite a different key set.**
Design §3.2 says combine XOR *and* SUM *and* count.
**Fix:** add `sum` to `KeyStats` and require it to match.

### V3 — Key-set check only runs for a column named `id` — High
**`src/verify.rs:403,468-471`** — `has_id = scols.iter().any(|c| c.name == "id")`; any other
PK (`user_id`, `uid`, composite, UUID) → `Skipped`, which counts as Clean. A `users` table
keyed on `uid` with half its rows dropped still exits 0.
**Fix:** derive the key column from the `TablePlan`/cursor rather than hardcoding `"id"`.

### V4 — `latest_key_stats` windows the whole Delta log before the size guard — High (Memory)
**`src/verify.rs:429-432`, `src/verify/delta.rs:103-114`** — incremental verify runs a
`row_number() OVER (PARTITION BY id ORDER BY cursor DESC)` over the **entire append-log**,
*before* the row-cap guard (which is keyed on the source-scoped count at `verify.rs:461`). A
source slice of 500k rows under the cap can sit over an 80M-row append-log → the window/sort
+ `count(distinct)`/`bit_xor(distinct)` hash-aggregate exhausts the 8 GB VM.
**Fix:** move the guard ahead of any Delta scan, cap by Delta row count too, and scope
`latest_key_stats` to the HWM.

### V5–V8 — Med
- **V5** `src/verify.rs:374-395` — schema check compares column *names* only; types are read
  but unused, so a column written with the wrong Delta type passes "schema ok."
- **V6** `src/verify/source.rs:161-163` + `verify.rs:118` — sampling is `ORDER BY id LIMIT
  100`, i.e. only the lowest 100 ids; recently-written rows are structurally never checked.
- **V7** `src/verify/delta.rs:103-114` vs `verify.rs:472-480` — Delta stats are not
  HWM-scoped while source stats are → asymmetric scope can raise a spurious discrepancy.
- **V8** `src/verify/source.rs:86-87` vs `delta.rs:75-76` — keys forced to signed 64-bit;
  `BIGINT UNSIGNED > 2^63` saturates on MariaDB but overflows to null on datafusion → false
  discrepancy on large unsigned keys.

## G. Low-severity findings

- **L1** `src/calendar.rs:7-19` — year found by stepping one year at a time (O(|years|)) and
  `remaining += year_len` can overflow near `i64::MIN`; a garbage epoch value hangs or panics
  rather than erroring cleanly. Fix: 400-year-cycle arithmetic + `checked_add`.
- **L2** `src/writer/datetime.rs:62-82` vs `85-86` — truncating division for `secs` but
  `div_euclid/rem_euclid` for sub-seconds disagree for **negative** (pre-1970) timestamps →
  wrong rendered string feeding the HWM. Fix: use `div_euclid/rem_euclid` for both.
- **L3** `src/writer/two_stream.rs:239-244`, `hwm.rs:64-69` — `UInt64` key cast `as i64`
  wraps negative above `i64::MAX`; the DELETE may then not match and a stale row survives.
- **L4** `src/writer/two_stream.rs:98,216` — dedup `ROW_NUMBER() OVER (PARTITION BY key ORDER
  BY key)` orders by the partition column, so which duplicate survives is nondeterministic;
  a crash-and-rerun could commit a different value. Fix: order by the version/timestamp DESC.
- **L5** `src/discovery.rs:121-136` — index-presence check hardcodes `COLUMN_NAME =
  'updated_at'`, so a custom cursor column always warns "no index" spuriously.
- **L6** `src/writer/hwm.rs:18-27` — computes a single max via three O(n) `Vec`s + one heap
  `String` per row, purely transient; a single fold with no intermediates suffices.
- **L7** `src/writer.rs:230-231`, `two_stream.rs:168` — `read_hwm` reads only the single
  latest commit (`history(Some(1)).pop()`); a later non-HWM commit (compaction/OPTIMIZE/an
  append with `insert_id=None`) shadows a real HWM → treated as absent. Fix: scan history
  backward for the first commit that actually carries the HWM key.

## Prioritized remediation roadmap

**Fix before running the full export on the 8 GB VM:**
1. **M1** — replace `delete_then_append`'s `HashSet`+`IN`-list with a range/anti-join delete
   (unblocks shrinking the 512 MB stack too).
2. **C1** — keyset pagination for FullRefresh (correctness *and* O(n²)).
3. **R1** — stop mapping S3 errors to `None` in `read_hwm` (prevents duplicate rows).
4. **R2** — real key column in `extract_hwm_from_batch` + `bail!` on a full batch with no HWM
   advance (prevents the infinite duplicate loop).
5. **M4 / CF1 / CF2** — config guards: RAM-relative `TARGET_MEMORY_MB` ceiling,
   `DEFAULT_BATCH_SIZE>0`, `AVG_ROW_LENGTH` NULL fallback.

**Next:**
6. **M2 / M3** — stream extract → write; avoid the `concat_batches` 2× copy.
7. **V1–V4** — make `--verify` trustworthy (value aggregates, SUM in the fingerprint, real key
   column, guard-before-scan) before relying on it as the export's proof of correctness.
8. **R3 / R4 / R5** — SIGTERM handling, honest exit codes on interruption, durable `state.json`.

**Hardening:**
9. **D1 / D2 / D3** — additive schema evolution, NULL-timestamp backfill, persist the seed.
