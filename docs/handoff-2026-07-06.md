cargo test --lib                        # unit + lib tests, no Docker

Integration tests (`cargo test`, needs Docker: MariaDB + MinIO) are **not** run by `--lib`.

**Hard-won lesson:** do **not** trust a sub-agent's self-reported exit codes. Independently re-run `build` + `clippy --lib -- -D warnings` + `test --lib` and read the real output. During this session, agents repeatedly reported "all green" while clippy actually failed (`collapsible_if`, `format_in_format_args`) or diagnostics were stale. Always verify yourself.

## 4. Working conventions (from the user)

- **No `Co-Authored-By` (or any AI-attribution) trailer in commit messages.** Subject + body only.
- **Conventional-commit** style subjects (`fix(...)`, `feat(...)`, `docs(...)`).
- Work in the loop the user chose: **plan → confirm → implement+test → review → commit**, one finding at a time, **stopping for confirmation between steps**. The user picks scope/options at each plan gate.
- **Snapshot branch before starting each new fix** (`snapshot/pre-<step>-<date>`).
- Prefer **small, localized, reviewable diffs**. Never weaken an existing test assertion to make it pass.

## 5. Big caveat that spans the verify work

The V1b-1/V1b-2 value-verification **adapter SQL is only review-verified, not execution-tested.** `cargo test --lib` exercises the verdict logic via mocks; it does **not** prove that MySQL and datafusion render the per-column fingerprints identically. The single highest-value follow-up is a **Docker integration test** (testcontainers MariaDB + MinIO already used in `tests/integration.rs`) that writes known data through the real pipeline and asserts source vs Delta fingerprints match for each type family (integer, decimal, datetime, date, text) — including the documented blind spots in `docs/verify-value-checks.md`. Until that exists, treat cross-engine equality as *plausible, not proven*.

## 6. Remaining work — prioritized

### Tier 1 — next up (High)

#### C1 — full-refresh pagination: skip/dup rows + O(n²)  *(PLAN READY, decision pending)*
- **Where:** `src/query.rs::build_full_refresh_query_paged`, `src/orchestrator/full_refresh.rs`.
- **Bug:** `LIMIT n OFFSET k*n` with **no `ORDER BY`** → unstable order → rows skipped/duplicated across chunks; deep OFFSET → O(n²) rescans.
- **Fix:** keyset (seek) pagination — `WHERE {key} > {last_key} ORDER BY {key} ASC LIMIT {n}`, tracking the last key per chunk (mirror the incremental cursor; reuse `extract_max_id`).
- **Open decision (was at the confirmation gate when we stopped):** FullRefresh tables may have **no single-column key** to seek on (that mode is chosen when a table lacks `id`+`updated_at`). Fallback options:
  - **A (recommended):** keyset when a single-column PK/unique key exists; else keep OFFSET **but add `ORDER BY <all columns>`** so paging is at least stable. Correct everywhere; only keyless tables stay O(n²).
  - **B:** keyset when keyed; else fetch whole table in one query → **OOM risk on 8 GB** for keyless large tables.
  - **C:** require a key; fail loudly if none.
- **First step:** confirm how the orchestrator/discovery exposes a table's PK/unique key so you know when the keyed path applies.
- **Tests:** query-builder unit tests (keyset + keyless SQL); orchestrator loop test paging across chunks with no dup/skip.

#### R2 — HWM fails to advance → infinite duplicate-append loop  *(High)*
- **Where:** `src/orchestrator/incremental.rs` (loop 70–110), `src/writer/hwm.rs::extract_hwm_from_batch` (hardcodes `column_by_name("id")`).
- **Bug:** if the returned batch lacks the timestamp col OR an `id` col (dropped by schema-evolution filter, or a non-`id` key), `extract_hwm_from_batch` returns `None`, `current_hwm` never advances, and a full batch re-queries the same window forever → unbounded duplicate appends.
- **Fix:** (a) thread the real key-column name into `extract_hwm_from_batch` instead of hardcoding `"id"`; (b) if a **full** batch (`rows == batch_size`) yields no advanced HWM, `bail!` instead of re-querying.
- **Tests:** loop test where HWM can't advance → returns an error, not an infinite loop.

#### Verify Docker integration test  *(High follow-up; see §5)*
- Validates V1b-1/V1b-2 adapter SQL end-to-end. Without it, the value-verification correctness is unproven.

### Tier 2 — High memory / verify correctness
- **M2** (`src/extractor.rs:56`): `reader.collect()` materializes the whole query result in RAM (× the mysql client buffer). Stream batches into the writer instead of collecting.
- **M3** (`src/writer/two_stream.rs:40,209`): `concat_batches` doubles the source payload before MERGE/delete; `drop(batches)` early (M1 already did this for `delete_then_append`; `merge_batch` still needs it) or register without copying.
- **V3** (`src/verify.rs:403`): key-set verdict only runs when a column is literally named `id`; other PKs → `Skipped`→Clean (false confidence). Derive the key from the `TablePlan`/cursor.
- **V4** (`src/verify.rs:429`, `verify/delta.rs`): incremental `latest_key_stats` windows the whole append-log **before** the row-cap guard → OOM risk on a huge log. Move the guard ahead of the scan; cap by Delta rows too.
- **V7** (partially done): the **value-aggregate** path is now HWM-scoped on both sides (V1b-2), but the **key-set** (`latest_key_stats`) path is still not HWM-scoped. Finish it for the key check.
